Verificação das três funções vulneráveis no Supabase

Coleta: 23/10/2026, aproximadamente 11h07–11h10 (Brasília). Fontes primárias: conector Supabase, configuração de produção Vercel e código GitHub.

Resultado: SIM

As três definições SQL vulneráveis estão implantadas no banco configurado para produção do Elos OS. São SECURITY DEFINER, executáveis por anon e authenticated, com proprietário BYPASSRLS e sem validação de usuário, empresa ou permissão no corpo SQL.

Limites: a exposição HTTP pela Data API está NÃO COMPROVADA; o diff literal com o commit 39d858c está NÃO COMPROVADO, pois esse commit não foi encontrado no repositório remoto acessível. A conclusão “SIM” diz respeito às definições e permissões no banco; não afirma exploração, vazamento ou acesso HTTP comprovado.

Projeto correto e vínculo com produção

Supabase: elos-os-dev, referência uqxflulrjdnhzrhptyla, região ca-central-1, ACTIVE_HEALTHY. O nome “dev” não foi usado para presumir ambiente.

O projeto Vercel elos-os tem deployment READY com alvo production (dpl_EQkbzWrpscobcdXXypLJE2yTaFy3), branch main, repositório fabionicodemus-lang/elos-os e commit 460147e74be9b67c9cff2613b710a9cf0c264274. Sua variável NEXT_PUBLIC_SUPABASE_URL, destinada também a production, aponta para https://uqxflulrjdnhzrhptyla.supabase.co/rest/v1/. Isso vincula o banco auditado à configuração de produção. Não foi executado um fluxo funcional da aplicação nem inspecionado o ambiente interno de um processo em execução.

CREATE OR REPLACE FUNCTION public.refresh_execution_service_contract_measurements(p_contract_id uuid)
 RETURNS void
 LANGUAGE plpgsql
 SECURITY DEFINER
 SET search_path TO 'public'
AS $function$
begin
 update public.execution_service_contract_stages s set
  measured_quantity=s.opening_measured_quantity+coalesce(x.quantity,0),
  measured_value=s.opening_measured_value+coalesce(x.amount,0),updated_at=now()
 from (
  select s0.id stage_id,coalesce(sum(mi.current_quantity) filter(where m.status in('approved','invoiced','paid')),0) quantity,
   coalesce(sum(mi.current_amount) filter(where m.status in('approved','invoiced','paid')),0) amount
  from public.execution_service_contract_stages s0
  left join public.execution_contract_measurement_items mi on mi.contract_stage_id=s0.id
  left join public.execution_contract_measurements m on m.id=mi.measurement_id
  where s0.contract_id=p_contract_id group by s0.id
 ) x where s.id=x.stage_id;

 update public.execution_service_contract_items ci set measured_quantity=coalesce(x.quantity,0),measured_value=coalesce(x.amount,0),updated_at=now()
 from (
  select mi.contract_item_id,sum(mi.current_quantity) quantity,sum(mi.current_amount) amount
  from public.execution_contract_measurement_items mi join public.execution_contract_measurements m on m.id=mi.measurement_id
  where mi.contract_id=p_contract_id and m.status in('approved','invoiced','paid') group by mi.contract_item_id
 ) x where ci.id=x.contract_item_id;
 update public.execution_service_contract_items ci set measured_quantity=0,measured_value=0,updated_at=now()
 where ci.contract_id=p_contract_id and not exists(select 1 from public.execution_contract_measurement_items mi join public.execution_contract_measurements m on m.id=mi.measurement_id where mi.contract_item_id=ci.id and m.status in('approved','invoiced','paid'));

 update public.execution_service_contracts c set measured_value=coalesce(x.measured,0),retained_value=coalesce(x.retained,0),invoiced_value=coalesce(x.invoiced,0),paid_value=coalesce(x.paid,0),updated_at=now()
 from (
  select p_contract_id contract_id,coalesce(sum(gross_amount) filter(where status in('approved','invoiced','paid')),0) measured,
   coalesce(sum(contractual_retention_amount+guarantee_retention_amount) filter(where status in('approved','invoiced','paid')),0) retained,
   coalesce(sum(net_amount) filter(where status in('invoiced','paid')),0) invoiced,coalesce(sum(paid_amount) filter(where status='paid'),0) paid
  from public.execution_contract_measurements where contract_id=p_contract_id
 ) x where c.id=x.contract_id;
end $function$

CREATE OR REPLACE FUNCTION public.refresh_execution_service_contract_value(p_contract_id uuid)
 RETURNS numeric
 LANGUAGE plpgsql
 SECURITY DEFINER
 SET search_path TO 'public'
AS $function$
declare total numeric; amendment_total numeric; begin
  select coalesce(sum(total_value),0) into total from public.execution_service_contract_items where contract_id=p_contract_id;
  select coalesce(sum(value_change),0) into amendment_total from public.execution_service_contract_amendments where contract_id=p_contract_id;
  update public.execution_service_contracts set original_value=total,amendments_value=amendment_total,current_value=greatest(0,total+amendment_total),updated_at=now() where id=p_contract_id;
  return greatest(0,total+amendment_total);
end; $function$

RLS e proteções auxiliares

As oito tabelas relacionadas têm RLS ativo, FORCE RLS=false e proprietário postgres. As três funções executam como postgres, com BYPASSRLS=true; por isso o RLS não fornece isolamento ao chamador dentro dessas funções.

Há funções de autorização já implantadas, como has_company_permission(target_company_id uuid, target_permission text), que verifica membership.user_id=auth.uid(), associação e papel ativos e a permissão; as três funções analisadas não a chamam.

Nos quatro alvos de UPDATE (contratos, itens, etapas e ordens), os triggers de negócio encontrados no contrato aplicam-se a INSERT e a UPDATE de status. O trigger de auditoria registra alterações, mas seu corpo não autoriza usuário/empresa. Não há evidência de uma barreira de autorização nesses triggers para os recálculos analisados.

Impacto e recomendações

Prioridade alta: os grants e os corpos permitem ao chamador com EXECUTE fornecer UUIDs de objetos sem comprovar vínculo com a empresa. As operações podem recalcular e gravar valores derivados de contratos e ordens; a primeira também retorna um total. A confirmação de exploração pela internet depende da configuração da Data API e não foi tentada.

  1. Recuperar/publicar o patch exato de 39d858c e revisar a migration, incluindo todos os chamadores internos das três funções.
  2. Preparar contenção dos grants: remover execução de PUBLIC e anon; para helpers internos, revisar também authenticated. Apenas remover o grant de anon não basta se PUBLIC continua concedendo EXECUTE. Aplicar somente em uma etapa posterior autorizada.
  3. Para qualquer chamada legítima direta, resolver a empresa/obra do objeto no banco, exigir usuário autenticado e permissão específica na empresa antes do recálculo. Reaproveitar o helper de autorização existente após revisar a política adequada.
  4. Preferir helper em schema privado, acessado por funções de entrada autorizadas. Avaliar SECURITY INVOKER somente com os chamadores e políticas RLS; uma troca mecânica pode quebrar fluxos ou não resolver todos os acessos.
  5. Obter a configuração efetiva da Data API em modo de leitura: enabled, db_schema(s), extra search path e schema padrão. Verificar presença dos endpoints via metadados, sem executar RPCs.
  6. Validar o patch em ambiente isolado com empresas/usuários fictícios: anônimo, usuário da empresa A, usuário da empresa B, sem permissão e chamada interna legítima. Após eventual implantação autorizada, repetir esta coleta de definições e grants.

Essas recomendações não foram aplicadas. Não há evidência coletada de exploração anterior; logs e dados financeiros não foram examinados.

Escopo de execução e rastreabilidade

Todas as consultas ao banco foram SELECT de pg_catalog, funções nativas de inspeção de catálogo, settings e permissões. As definições SQL contêm UPDATE porque esse é o código implantado; foram apenas lidas como texto. Nenhuma das três RPCs foi invocada, nenhum DDL/DML foi enviado e nenhum registro financeiro de cliente foi consultado.

Identificação: list_projects e get_project. Funções: pg_proc, pg_namespace, pg_language, pg_roles, pg_get_functiondef, pg_get_function_arguments, pg_get_function_identity_arguments, pg_get_function_result, has_function_privilege e has_schema_privilege. RLS: pg_class. Triggers: pg_trigger + pg_get_triggerdef. Exposição: current_setting, pg_db_role_setting e pg_settings. MD5 registra o texto da definição para comparação, sem pretensão de assinatura criptográfica.
